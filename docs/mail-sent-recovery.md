# Sent: отправка, синхронизация и восстановление

Ручная отправка заранее создаёт настоящий `Message-ID`, локальную запись и приватный MIME-файл в `storage/app/private/mail-sent`. Тот же MIME передаётся SMTP. Только положительный ответ транспорта переводит `delivery_status` в `sent`. Ошибка IMAP после этого не означает ошибку отправки.

Архиватор ищет в настроенной папке Sent точный `Message-ID`, проверяя заголовок через `BODY.PEEK[HEADER]`. Если SMTP-провайдер ещё не сохранил копию, повторная попытка выполняется через 15 секунд. Для адресов из `MAIL_SENT_COPY_APPEND_MAILBOXES` (по умолчанию `com@food-server.ru,office@180022.ru`) отсутствующая копия добавляется через IMAP APPEND. Повтор после потерянного ответа APPEND сначала ищет существующую копию. SMTP при восстановлении не вызывается.

Синхронизация переиспользует исходную локальную запись. Её ID, вложения и CRM-связи сохраняются. Неоднозначные совпадения не объединяются автоматически. Состояния `prepared`, `sending`, `unknown`, `failed` не участвуют в автоматическом APPEND: нельзя изображать отправленным письмо с неподтверждённой доставкой.

## Команды после развертывания и миграций

Запускать из каталога приложения. Команды не отправляют сообщения получателям.

Просмотр возможности восстановления старых локальных копий com (по умолчанию dry-run, писем не меняет):

```sh
php artisan mail:reconstruct-legacy-sent --mailbox=com@food-server.ru
```

Ожидаемый результат для состояния, проверенного 27.09.2026: 14 строк `eligible`, две строки `skipped / attachment_completeness_unproven` (локальные ID 3693 и 3764). Если появились другие письма в серверной Sent, выполнение остановится, чтобы не создавать дубликаты.

Создание проверенных архивных копий на сервере:

```sh
php artisan mail:reconstruct-legacy-sent --mailbox=com@food-server.ru --apply
```

У копий будет новый стабильный Message-ID, заголовки `X-Pischeprom-Reconstructed-From` / `X-Pischeprom-Archive-Type` и `sent_copy_status=reconstructed`. Это восстановленный архив, а не исходный SMTP MIME. Даты, получатели и доступное тело сохраняются. Повторный запуск распознаёт предыдущие реконструкции по точному ID; SMTP не используется. Письма с вложениями пропускаются, поскольку старый формат не сохранял доказательство полного количества вложений.

Для office старые записи `@local.pischeprom` остаются отдельными архивными копиями с `sent_copy_status=legacy`: наличие оригиналов в Sent блокирует массовую реконструкцию. Тема и дата не считаются доказательством тождества.

Повтор синхронизации новых подтверждённо отправленных писем:

```sh
php artisan mail:reconcile-sent --mailbox=com@food-server.ru --limit=100
php artisan mail:reconcile-sent --mailbox=office@180022.ru --limit=100
```

Команда обрабатывает только `delivery_status=sent`, отсутствие UID, сохранённый MIME и `sent_copy_status=pending/failed`. Обычный механизм — `ArchiveSentMailJob` в очереди `mail-sync`; планировщик также вызывает reconcile для случаев, когда постановка job не удалась.

## Неопределённая доставка

Потерянный ответ SMTP оставляет `delivery_status=unknown`. Повтор того же idempotency key не отправляет письмо заново. Если подтверждение SMTP получено, но последующая запись в БД недоступна, клиент получает предупреждение о принятом письме, а сохранённая строка может остаться `sending`. Такие записи требуют сверки с журналом провайдера или точной серверной копией. Не следует вручную переводить их в `sent` или повторять SMTP без проверки.

Приватный `.eml` сохраняется для повторного APPEND и расследования; его путь исключён из JSON модели. Ошибки jobs содержат только безопасный код и не сериализуют ответы SMTP/IMAP, MIME или пароли.

# Резервные копии БД, архива Avito и ключей

## Активация и подтверждение

Workflow `.github/workflows/production-backups.yml` управляет операциями на
production VPS через закреплённый SSH host key. Разрешена только актуальная
ветка `main`, причём её SHA должен совпадать с уже развёрнутым приложением.
Деплой выполняется существующим workflow `Verify and deploy to production`.
Копии, ключи и персональные данные не проходят через GitHub Actions.

Сначала запускается `plan`: read-only инвентаризация Yandex Cloud и безопасная
диагностика VPS. Для активации требуется выбранное владельцем независимое
хранилище. Подготовленный вариант — отдельный закрытый бакет
`pischeprom-backups-<последние 8 символов YC_FOLDER_ID>` в существующем Yandex
Cloud, с пределом 100 GiB и версионированием. Публичные/GIS бакеты не меняются.

`apply` создаёт выделенный сервисный аккаунт, бакет и Lockbox escrow, ставит
restic из подписанного репозитория ОС и устанавливает systemd units. Затем
выполняет первую копию и полное пробное восстановление. Таймеры включаются
**только после успешных обеих операций**. Повторный `apply` использует прежний
пароль и репозиторий. Ошибка доступа не считается поводом заменить ключ.

Сервисный аккаунт OIDC должен уже иметь права создавать/настраивать бакет,
создавать сервисный аккаунт и его статический ключ, создавать/читать Lockbox.
Provisioner сам себе права каталога не выдаёт. Отказ API требует проверки
имеющихся IAM-прав, а не ослабления публичного доступа.

Ручные действия workflow: `run`, `verify`, `status`. Ежедневный Actions cron
в 06:15 UTC проверяет состояние, включая активность таймеров. Неудача запуска
видна как failed workflow и использует штатные уведомления GitHub владельца.

## Состав и расписание

- Ежедневно в 03:10–03:15 по Москве: согласованный дамп **всей БД**, все файлы
  текущего и исторических локальных дисков Avito, manifest SHA-256, `APP_KEY`,
  `APP_PREVIOUS_KEYS`, cipher, пути дисков и SHA приложения.
- По воскресеньям в 05:30–05:35: скачивание последнего снимка и полная проверка
  восстановления, контрольных сумм, архивных ссылок и расшифровки Avito-полей.
- Нет автоматического `forget`, `prune`, lifecycle expiry или удаления старых
  снимков. Они сохраняются без ограничения по возрасту. Увеличение ёмкости и
  изменение политики хранения — отдельная эксплуатационная операция.

Шифрование выполняет restic на VPS. Его случайный пароль независим от
`APP_KEY`, хранится в закрытом `/etc/pischeprom-backup/restic-password` и в
Lockbox с защитой удаления. Ключи приложения находятся внутри зашифрованного
снимка: потеря VPS не создаёт зависимости «ключ внутри собственной копии».
Потеря пароля restic делает восстановление невозможным
([документация restic](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)).

Пишущий аккаунт может читать/добавлять объекты `production/*` и удалять только
служебные locks. Удаление данных и версий ему запрещено. Версионирование
сохраняет прежние версии при перезаписи; это не десятилетний Object Lock.
Администратор облака по-прежнему управляет бакетом и правами.

## Изоляция и контроль ошибок

Runtime работает от непривилегированного владельца приложения. Закрытые
конфигурация и рабочая область находятся вне каталога приложения, поэтому
деплой не меняет их права. Systemd предоставляет запись только в эти области.
Дамп защищён 0600/0700 и удаляется после загрузки либо ошибки. Временные данные
восстановления удаляются после проверки. Нештатное выключение питания может
оставить закрытые временные данные до ручной очистки/следующего запуска.

MySQL/MariaDB: `--single-transaction` допускается только для InnoDB. Проверка
создаёт **отдельный сервер** с новым datadir и Unix socket, без TCP, MySQL X и
event scheduler. На production MySQL импорт не выполняется. Существующие
views/routines/events/triggers пока блокируют активацию: квалифицированные
ссылки на исходное имя БД требуют отдельного сценария проверки. SQLite
снимается через `VACUUM INTO`; открытая WAL-БД не копируется как обычный файл.

Требуются `pdo_sqlite`, для MySQL — его клиент, dump utility и уже установленный
серверный binary. Перед каждой операцией проверяется запас диска: три объёма
данных плюс 1 GiB. Снимок не совмещается с миграциями приложения; конкурирующие
операции резервирования не могут удалить staging друг друга.

Состояние хранится в `/var/lib/pischeprom-backup/state.json`; закрытый лог
последней операции — `last-operation.log`. В Actions/journal выходят только
агрегаты и фиксированные коды ошибок. Состояние считается исправным при
копии моложе 36 часов, успешном восстановлении моложе 9 дней и отсутствии
ошибки последней операции каждого типа. Успешная копия не скрывает провал
последующего восстановления.

## Восстановление после потери VPS

1. С защищённой машины администратора получить пароль из Lockbox. ID секрета
   виден в результате provisioner и в облачном каталоге; имя
   `<имя бакета>-repository-key`. Нельзя генерировать новый пароль или делать
   `restic init` для старого репозитория.
2. Выдать временные **read-only** S3 credentials для нужного бакета новому
   серверу восстановления. Старый static secret после потери VPS не извлекается
   из IAM; поэтому повторный `apply` намеренно откажет без локальных credentials.
3. Создать закрытые файлы пароля/настроек, задать `RESTIC_REPOSITORY` вида
   `s3:https://storage.yandexcloud.net/<bucket>/production`, AWS credentials
   и `RESTIC_PASSWORD_FILE`. Не передавать секреты в аргументах/чатах/Actions.
4. Выполнить `restic snapshots`, затем `restic restore <snapshot-id> --target
   <private-directory> --verify`. `recovery.json` лежит внутри восстановленного
   `/var/lib/pischeprom-backup/current`; абсолютные исходные пути восстановлены
   под указанной целевой директорией.
5. Проверить SHA-256 дампа и файлов, восстановить БД на **новом изолированном**
   сервере. Восстановить `APP_KEY`, предыдущие ключи, cipher и соответствующие
   архивные диски; использовать сохранённый SHA приложения и миграции.
   Не запускать очереди, AI, Avito или иные внешние интеграции на тестовой копии.
6. Запустить `verify-restored-application.php` с закрытым JSON подключения к
   тестовой БД `backup_verify_*` (или SQLite-копией). После проверки доступности
   старых чатов/CRM и вложений отдельно выполнить переключение приложения.
7. Отозвать старые credentials потерянного VPS и временные recovery credentials,
   восстановить расписание копирования. Пароль репозитория при этом сохраняется.

Если злоумышленник перезаписал объекты текущей версии, администратор сначала
восстанавливает прежние версии в бакете; writer не имеет права удалять версии.

## Границы гарантии

Десятилетнее хранение требует оплаты/доступности облака, сохранения доступа
администратора к Lockbox, роста квоты вместе с архивом и наблюдения за ошибками.
Квота 100 GiB ограничивает расход и при заполнении остановит новые копии; это
будет ошибкой backup/status, а не поводом автоматически удалить старые снимки.
Состояние `healthy` относится к регулярности операций, не к будущей оплате.

Копируются уже полученные вложения. Ещё не скачанные или исчезнувшие из Avito
файлы резервирование восстановить не может. `plan` показывает их количество
как `unarchived_attachments`. Удалённые до первого импорта сообщения также
отсутствуют в локальном архиве.

Проверки в CI используют только синтетические данные: настоящий restic-снимок,
удаление исходной SQLite БД/файла/ключа и восстановление из зашифрованной копии;
отдельные регрессии повреждений, ротации ключей, блокировок и прав облака.

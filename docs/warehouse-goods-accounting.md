# Учёт Goods на складе и списание Sale

## Результат аудита

`Ameise/warehouses` получает остатки из `GET /api/good-warehouse-stock`.
Количество — сумма `good_stock_movements.quantity_delta` отдельно для каждого
склада, товара и единицы измерения. Закупки уже создавали приход; оба пути
создания Sale и старый API `goodsales` не создавали расход. Поэтому продажи
не уменьшали остаток.

У Sale нет статуса «черновик/проведён». Сохранённая позиция `good_sale` считается
проведённой; банковский `payment_status` не управляет складом. Сохранение пустой
шапки Sale не списывает товар. Добавление позиции списывает его сразу.

## Правила и защиты

- Каждая позиция Sale создаёт расход на системном складе с `code = goods`.
  `source_type = good_sale`, `source_id = good_sale.id`, `sale_id = sales.id`.
  Существующий уникальный индекс `(source_type, source_id)` предотвращает
  повторное движение при повторной синхронизации.
- Продажа, её позиции, складские движения и пересчёт суммы добавленной позиции
  сохраняются в одной транзакции. Ошибка откатывает всю операцию.
- Новые списания при нехватке запрещены с HTTP 422. В сообщении указаны товар,
  склад, единица, доступное количество и размер списания. Остатки другого склада,
  другой единицы или «без единицы» не используются; автоматических коэффициентов
  пересчёта в приложении нет. Дробное количество продажи имеет точность 6 знаков.
- Общий `GoodStockMutationService` блокирует строки Goods по возрастанию ID,
  затем читает движения с блокировкой. Это сериализует конкурирующие продажи,
  ручные списания и изменения закупок, включая первое движение нового остатка.
  Чтение с блокировкой исключает использование старого снимка MySQL
  `REPEATABLE READ`. Транзакции повторяются до трёх раз при взаимной блокировке.
- Ручное уменьшение/удаление использованного прихода и уменьшение/удаление
  использованной закупки также запрещены. Исторический отрицательный остаток
  можно улучшать, но нельзя дополнительно уменьшать обычными операциями.
- Складское движение Sale или Purchase нельзя менять/удалять через ручной API.
  Системный склад нельзя удалить или переименовать его код. Внешние ключи
  запрещают каскадное удаление складской истории вместе с товарами, складами,
  единицами, продажами и закупками. Товар с движениями следует снимать с публикации.
- Все входы изменения продаж, закупок, складов и движений требуют авторизацию
  и подтверждённую почту. Доступ имеет незаблокированный администратор CRM либо
  сотрудник с существующим правом `warehouse.move` (guard `crm`). Для сотрудников
  это право должно быть назначено до включения обновления.
- Формы продаж передают `request_id` (UUID). Повтор того же запроса возвращает
  сохранённую Sale без нового списания или увеличения суммы. Повтор UUID с другим
  действием/содержимым даёт HTTP 409. Для внешних клиентов поле необязательно для
  совместимости: при сетевом повторе необходимо передавать прежний `request_id`.
  Разные UUID означают разные операции. При изменении данных после ошибки
  конфликта следует начать новую операцию с новым UUID.
- Уведомления о доступности ставятся в очередь только после commit; при переносе
  ручного движения обновляется доступность обоих товаров, включая прежний.
- Отмена/редактирование Sale и удаление её позиции ранее не были реализованы.
  Эти API теперь явно возвращают 405. Добавление позиции в Sale поддерживается.
  Возврат товара и отмена документа требуют отдельного согласованного процесса.

## Стоимость и даты

Расход использует среднюю стоимость доступного остатка, а не цену продажи:
`SUM(quantity_delta * unit_price) / SUM(quantity_delta)`. При повторной
синхронизации той же позиции себестоимость сохраняется. Для исторической продажи
без положительного остатка используется средняя стоимость зарегистрированных
приходов в той же единице; при отсутствии приходов — 0.

Это складская оценка по имеющимся движениям, не FIFO и не полноценный пересчёт
себестоимости по датам. Дата расхода равна дате Sale. Текущий отчёт, как и до
изменения, суммирует все движения, включая документы с будущими датами.
Изменение старых закупочных цен не переоценивает автоматически последующие расходы.

## Включение и ранее сохранённые продажи

Миграции меняют структуру и ограничения; автоматически списывать всю историю они
не будут. Рабочая база при разработке не пересчитывается.

1. Применить миграции и обновить frontend обычным процессом развёртывания:

   ```sh
   php artisan migrate --force
   npm run build
   ```

   Сборка проверена на Node.js 22.18. Системный Node.js 16 несовместим с установленным Vite.

2. Выполнить сверку без записи:

   ```sh
   php artisan goods-stock:reconcile-sales
   ```

   Команда показывает отсутствующие/отличающиеся расходы, некорректные позиции,
   прогноз отрицательных остатков и наличие ручных расходных движений затронутых
   товаров. Таблицы диагностик ограничены первыми 50 строками; счётчики полные.
   Для отдельной продажи: `--sale=123`; параметр можно повторять.

3. Сверить ручные списания и начальные остатки. Если продажи уже списывались вручную,
   их необходимо сопоставить: команда не угадывает связь между ручным движением и
   Sale. Иначе ручной расход и автоматический расход посчитаются вместе. Проверить
   единицы измерения приходов и продаж. Некорректные позиции блокируют применение
   до исправления.

4. После проверки применить расходы сохранённых продаж:

   ```sh
   php artisan goods-stock:reconcile-sales --apply
   ```

   Для истории допускается отрицательный остаток: факт продажи не скрывается из-за
   отсутствующего прихода. Дефицит виден в складском отчёте. Каждая Sale обрабатывается
   атомарно; команду можно повторить после прерывания без дублирования движений.
   Для согласованной первичной сверки выполняйте её в период без изменения документов;
   предварительный отчёт представляет снимок, а не резервирует остатки.

5. Повторить сверку, проверить `Ameise/warehouses` и устранить дефицит по фактическим
   документам. Проверить работу очереди обновления доступности Goods.

Откат миграции связи Sale запрещён, пока существуют её складские движения:
удаление этой связи не должно незаметно вернуть проданные товары на склад.

## Проверки

Целевые тесты покрывают продажу и legacy API, добавление позиции, повторную
синхронизацию/повтор запроса, дробные величины, дефицит и откат нескольких позиций,
разные склады/единицы, себестоимость, права доступа, защиту движения и каскадов,
изменение закупки после продажи, уведомления после commit и историческую сверку.

```sh
php artisan test --filter='SaleGoodsStockTest|SaleGoodAttachmentTest|PurchaseGoodsStockTest|GoodStockMutationTest|WarehouseMutationAuthorizationTest|SaleStockIdempotencyTest|GoodStockAlertTest'
```

На отдельном MySQL 9.0.1 с временными каталогом данных и сокетом проверены два
PHP-процесса, списывающие по 4 из остатка 5: одно списание проходит, второе получает
ошибку, остаток равен 1. Повторён сценарий `REPEATABLE READ`, в котором вторая
транзакция заранее прочитала 5, а после первого списания получила блокировку:
проверка использует актуальный остаток 1 и отклоняет повторное списание.

Прямые SQL-изменения `good_sale`, `good_purchase` или журнала обходят сервисы
приложения. Импорт должен использовать эти сервисы и транзакции; после внешнего
импорта продаж необходима сверка. Миграция не исправляет вручную изменённую историю.

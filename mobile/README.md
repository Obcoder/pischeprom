# Заказы на Android

Внутренний интерфейс к существующему Laravel: Vue 3 + Vuetify + Capacitor 8.
Приложение содержит собственные мобильные экраны и обращается к JSON API
`/api/mobile/v1`. Товары, покупатели, заказы, продажи и складские движения
остаются в существующей базе. Отдельный сервер не нужен.

## Что входит в первый модуль

- Вход сотрудника, включая двухфакторное подтверждение, если оно включено.
- Карточки заказов, поиск по номеру и покупателю, фильтры «Сегодня»,
  «Ожидают сборки», «Готовы к отгрузке», «Отгружены».
- Состав заказа, сумма, склад, ответственный за сборку, предупреждения.
- Адреса доставки в списке и карточке, переход в Яндекс Карты, звонок по
  контактному телефону заказа через стандартный набор номера Android.
- Экран «Карта» с адресами выбранных заказов и переходом от точки к заказу.
- Плановая дата доставки, её изменение из мобильной карточки и Ameise;
  общий выбор дня для списка и карты, фильтр «Без даты».
- Автомобильный маршрут на выбранный день с вводом точки выезда, порядком
  остановок, временем в пути и переходом в Яндекс Карты по участкам.
- Проверка полного количества и явный выбор единицы измерения для каждой строки.
- Подготовка заказа и отдельное подтверждение отгрузки с результатом продажи.
- Защита от повторного проведения и устаревших данных.

На этом этапе поддерживается **полная отгрузка в RUB с системного склада
`goods`**, как в существующем проведении продаж. Частичная отгрузка, возвраты,
пересчёт между кг/упаковками и другие склады не реализованы. Количество
сверяется с заказом; изменять состав и цены нужно в существующем кабинете.
Если округление каждой позиции до копеек меняет итоговую сумму заказа,
отгрузка блокируется: цены нужно уточнить в основном приложении.
Единица измерения выбирается сотрудником, потому что в прежних заказах её
не было. Ответственный — сотрудник, выполнивший подготовку.

## Подготовка Laravel

Развернуть изменения обычным способом на существующем сервере и применить
миграции:

```sh
php artisan migrate --force
php artisan optimize:clear
```

Команды приведены для оператора развёртывания; создание исходников приложения
само по себе не изменяет рабочую базу.

При штатном развёртывании через GitHub Actions мобильные тесты проходят до
обновления сервера. После обновления `scripts/check-production-mobile.php`
проверяет схему заказов и HTTPS API без пароля и создания заказов или продаж:
пустой `POST /api/mobile/v1/auth/login` должен вернуть JSON с HTTP 422,
а `GET /api/mobile/v1/orders` без токена — HTTP 401.
HTTP 404 на маршруте входа означает, что мобильный API ещё не развёрнут
либо не обновлён кэш маршрутов. Переустановка APK эту серверную ошибку не исправляет.

Доступ получает активная учётная запись с подтверждённой почтой:
сотрудник (`type=employee`) с существующим правом `warehouse.move` в guard
`crm` либо администратор `admin` в этом guard. Права проверяются при каждом
запросе; блокировка пользователя или отзыв права сразу запрещает операции.

Настройки сервера (при необходимости в его `.env`):

```dotenv
MOBILE_TOKEN_TTL_MINUTES=480
MOBILE_ALLOWED_ORIGINS=https://localhost
MOBILE_ALLOW_NEGATIVE_STOCK=true
```

Для разработки в браузере добавить его точный origin, например:
`MOBILE_ALLOWED_ORIGINS=https://localhost,http://127.0.0.1:5174`.
Android использует нативный HTTP-клиент Capacitor. Серверу нужен действующий
HTTPS-сертификат. Мобильные запросы не используют cookie административного
кабинета и CSRF-сессию.

### Временная отгрузка без остатка

По запросу владельца для мобильного API временно включён
`MOBILE_ALLOW_NEGATIVE_STOCK=true` (также значение по умолчанию).
Недостаточный остаток показывается предупреждением, но не блокирует сборку
и отгрузку. Создаются обычная продажа и складские движения; остаток может
стать отрицательным. При отсутствии приходов себестоимость определяется
существующим складским механизмом, а не ценой продажи.
Чтобы вернуть запрет, задать `MOBILE_ALLOW_NEGATIVE_STOCK=false` в `.env`
сервера и выполнить `php artisan config:cache`. Переустановка APK для этого
не нужна. Настройка применяется только к мобильным отгрузкам; остальные
проверки заказа, прав, единиц измерения и повторного проведения сохраняются.

### Карта доставок

Для встроенной карты используется существующая настройка сервера
`YANDEX_MAPS_API_KEY` — ключ сервиса JavaScript API и Геокодер Яндекс.Карт.
После её изменения выполнить `php artisan config:cache`; ключ не нужно
включать в APK. Настройки карты доступны только авторизованным сотрудникам.
При необходимости коммерческого подключения SDK его адрес задаётся
существующим `YANDEX_MAP_SCRIPT_URL`.

Ключ и разрешённые источники настраиваются в
[кабинете Яндекса](https://developer.tech.yandex.ru/): для текущего Capacitor
источник страницы — `https://localhost`, для браузера — адрес страницы.
Проверить ограничения ключа на реальном телефоне по
[инструкции для WebView](https://yandex.ru/maps-api/docs/js-api/limit.html).
Использование карты во внутреннем приложении должно соответствовать
подключённому тарифу Яндекса. Без ключа экран сохраняет список адресов
и ссылки на отдельные адреса в Яндекс Картах.

Карта использует адреса доставки самого заказа, а не юридический адрес
покупателя. Геокодирование выполняется при открытии карты; результаты
не записываются в отдельный справочник. Адреса, которые не удалось точно
найти, остаются в списке для проверки. Телефон открывает набор номера:
сотрудник подтверждает звонок в телефонном приложении Samsung.

Адрес и телефон включены в проверку версии заказа. После обновления с 1.0
ранее подтверждённую сборку потребуется сверить и подтвердить повторно.

### Дни доставки и маршрут

`delivery_date` — календарная дата `YYYY-MM-DD`, отдельная от даты создания
заказа и существующего текстового пожелания по времени доставки.
Прежние заказы остаются без назначенной даты: найти их можно через «Без даты».
Дату можно перенести или очистить, в том числе после складской отгрузки.
Отдельное сохранение даты не меняет продажи, движения и подтверждённую сборку.
Версия заказа обновляется; параллельное изменение требует обновить карточку.

В Ameise дата доступна в таблице, фильтрах, форме создания и карточке заказа.
Планирование доступно активному сотруднику с подтверждённой почтой и правом
`orders.edit` или `warehouse.move`, а также CRM-администратору. При создании
используется `orders.create` вместо `orders.edit`.

На карте сначала выбрать день, затем при необходимости нажать «Все доставки
дня»: поиск и фильтр статуса тоже ограничивают набор остановок. Отгрузка со
склада не означает доставку покупателю, поэтому отгруженные заказы доступны
в дневном маршруте. Ввести точный адрес отправления и выбрать, нужен ли возврат.
Расчёт запускается только кнопкой; нераспознанные адреса нужно уточнить до него.

До 8 адресов порядок минимизирует сумму направленных дорожных времён Яндекса
точным перебором состояний. Для 9–50 адресов используется приближённый выбор
по дорожному времени из трёх ближайших кандидатов; интерфейс явно обозначает
этот режим. Это один автомобиль, без временных окон и времени разгрузки.
Пробки оцениваются на момент расчёта, а не прогнозируются на выбранную дату.
При изменении дня, адреса отправления или потере связи прежний расчёт отменяется.

Порядок ищется по реальным автомобильным маршрутам JavaScript API Яндекса.
Прямое расстояние используется только для отбора кандидатов в приближённом
режиме. Расчёт одного дня ограничен 160 парными обращениями; отображение
и ссылки навигации разбиваются на участки до 10 точек согласно
[ограничениям API](https://yandex.ru/dev/jsapi-v2-1/doc/ru/v2-1/dg/concepts/router/multiRouter).
Промежуточные оценки хранятся только в памяти текущего экрана.

### Активация ключа при штатном деплое

Для автоматической установки ключа можно задать GitHub Actions secret
`YANDEX_MAPS_API_KEY` в production environment или репозитории. Необязательная
Actions variable `YANDEX_MAP_SCRIPT_URL` выбирает стандартный или enterprise SDK.
Workflow передаёт значения в приватном временном файле по SSH и обновляет
только настройки Яндекс.Карт в серверном `.env`, после чего штатно пересоздаёт
кэш конфигурации. Ключ не входит в Git, APK, frontend artifact или логи.
Пустой secret сохраняет существующую серверную настройку.

Ключ выпускает владелец аккаунта в [кабинете Яндекса](https://developer.tech.yandex.ru/)
для сервиса JavaScript API и HTTP Геокодер. Карта, геокодер и маршрутизация
должны быть доступны по выбранному тарифу; ключи Yandex Cloud, Search или
Static Maps не заменяют этот ключ. После подключения обновить карту в приложении.

Токен имеет единственную область `mobile:orders`, срок действия и ограничения
маршрутов. Выход отзывает текущий токен. Пароль и токен не сохраняются на
диск телефона: после завершения процесса приложения требуется новый вход.
Истёкшие токены можно удалять штатной командой Sanctum
`php artisan sanctum:prune-expired --hours=24`.

## Сборка и запуск

Нужны Node.js 22.12+ (подойдёт актуальная LTS), Android Studio 2025.2.1+,
JDK 21, Android SDK Platform 36 и Android SDK Build-Tools.
Официальные инструкции: [окружение Capacitor](https://capacitorjs.com/docs/getting-started/environment-setup),
[рабочий процесс](https://capacitorjs.com/docs/basics/workflow).

Из корня репозитория:

```sh
npm ci
cp mobile/.env.example mobile/.env.local
```

В `mobile/.env.local` указать **адрес существующего Laravel**:

```dotenv
VITE_MOBILE_API_URL=https://ваш-домен/api/mobile/v1
```

Адрес фиксируется при сборке. После его изменения повторить сборку и sync.
Секретов в `VITE_*` быть не должно. Без корректного HTTPS-адреса приложение
показывает ошибку настройки и не отправляет пароль.

```sh
npm run mobile:dev       # браузер, порт 5174
npm run mobile:build     # web-ресурсы в mobile/dist
npm run mobile:sync      # сборка + копирование ресурсов в Android
npm run mobile:android   # сборка + sync + открытие Android Studio
```

Android-проект уже находится в `mobile/android`, повторять `cap add` не нужно.
Идентификатор приложения: `ru.pischeprom.orders`. HTML/CSS/JS включены в APK;
`server.url` не используется, страницы административного кабинета не загружаются.

Для отладочного APK после `mobile:sync`:

```sh
cd mobile/android
./gradlew assembleDebug
```

Результат: `mobile/android/app/build/outputs/apk/debug/app-debug.apk`.
Для передачи сотрудникам создать подписанный release APK через
**Build → Generate Signed App Bundle or APK** в Android Studio. Ключ подписи
хранить вне Git и использовать тот же ключ для последующих обновлений.
Выпуск и установка APK не выполняют миграции сервера автоматически.

## API

| Метод | Путь после `/api/mobile/v1` | Назначение |
| --- | --- | --- |
| POST | `/auth/login` | `email`, `password`, `device_name`, при необходимости `two_factor_code` или `recovery_code` |
| GET | `/auth/me` | Текущий сотрудник и область токена |
| DELETE | `/auth/token` | Выход с текущего устройства |
| GET | `/orders` | `search`, `filter=all/today/awaiting/ready/shipped`, `delivery_date` или `delivery_unscheduled=1`, `page`, `per_page` |
| GET | `/orders/{id}` | Актуальная карточка и версия заказа |
| PATCH | `/orders/{id}/delivery-date` | `version`, `delivery_date: YYYY-MM-DD` или `null`; сохраняет сборку и складской учёт |
| GET | `/delivery-map/config` | Настройки встроенной карты, доступные сотруднику |
| GET | `/delivery-map/orders` | Адреса заказов для карты; те же поиск, фильтры и пагинация |
| PATCH | `/orders/{id}/prepare` | `version`, `items: [{id, quantity, measure_id}]` |
| POST | `/orders/{id}/ship` | `version`, `request_id` (UUID) |

После входа передавать `Authorization: Bearer <token>` и
`Accept: application/json`. Изменения требуют `Content-Type: application/json`.
Карточки возвращаются в `data`, список дополнен `meta` с пагинацией.

Версию нужно брать из последнего ответа сервера. После подготовки она меняется.
При `409` нужно заново открыть заказ и проверить изменения. При потере ответа
на отгрузку повторяется **тот же** `request_id` и версия. Мобильный клиент
сохраняет их в памяти до определённого результата. После перезапуска приложения
нужно открыть заказ: успешно проведённый заказ уже будет отгружен.

Подготовка не резервирует товар. При проведении остаток повторно проверяется
под блокировками с учётом `MOBILE_ALLOW_NEGATIVE_STOCK`. Заказ, продажа и
списание сохраняются в одной транзакции; при отключённой настройке нехватка
любой позиции откатывает всю операцию. Используются существующие
`SaleStockRequestService`, `GoodSaleStockSynchronizer` и
`GoodStockMutationService`. Себестоимость берётся из складских движений,
цена продажи — из заказа. Проведённый заказ защищён от изменения и удаления
через существующий редактор.

## Проверка

```sh
php artisan test --filter='Mobile|OrderManagementTest|SaleGoodsStockTest|SaleStockIdempotencyTest|GoodStockMutationTest|SaleGoodAttachmentTest|WarehouseMutationAuthorizationTest'
npm run mobile:test
npm run mobile:sync
```

PHP-тесты используют изолированную SQLite in-memory базу из `phpunit.xml`.
Перед использованием на рабочем складе проверить на тестовых данных реальный
телефон: вход, сборку, нехватку товара, изменение заказа из кабинета и потерю
связи при подтверждении. Конкурентное проведение на MySQL следует проверить
на тестовой копии серверной базы: SQLite не воспроизводит блокировки MySQL.
